# SNS予約投稿の運用

## リリース順序

1. 作業コピーから投稿・DB事前検査・CIの差分をレビューする。GitHub ActionsのmacOSジョブで監査サンドボックスを含む全件を確認する。
2. Supabaseの接続先が samurai-verify / jjefffbmwkgylbdpipsj と一致することを確認する。001〜004のファイルハッシュを復旧資料の値と照合し、対象DBで `supabase/ops/precheck_001_004.sql` を読み取り専用で実行する。001が適用済みなら001は再実行しない。既存行・定義の差・想定外のオブジェクトを検出したら適用を止める。
3. 承認後、必要なマイグレーションだけを順番に適用する。002の前は、承認済み・公開済みの行が下書きへ戻る影響を確認する。003の後は権限を検証し、004の後はRPCの実行権限と結果・監査の整合性を確認する。
4. 承認後、対象SNSアカウントに必要な認証情報を設定する。クラウド側では `QUIZ_BACKEND=supabase` と公開サイトのHTTPS URLを使う。秘密は環境変数に設定する。
5. Vercelの本番デプロイに既存の `vercel.json` を含めるとCron登録を伴うため、デプロイとCron有効化をまとめて承認する。スケジュールは毎日12:00 UTC（タイ19:00、日本21:00）。SNS送信は `CRON_SECRET` のBearer認証、`SNS_MODE=live`、既存の `SNS_LIVE_CONFIRM`、`CRON_PUBLISH_ENABLED=true` がそろったときに開始する。
6. 明示承認済みの試験投稿1件で、Macを閉じた状態の予約起動、解答ページ、X・Threads・Instagramの投稿IDと公開URL、連続起動で投稿が増えないことを確認する。Instagramは直接APIの単画像投稿を使用。Bufferカルーセルは別途承認と接続検証を行う。

## 監視

- VercelのCron実行と関数ログを確認し、未起動、401、500、`state: disabled` を切り分ける。
- Supabaseの `quiz_post_log` と `quiz_post_attempts` で、媒体ごとに予約時刻、試行回数、結果、外部IDを突合する。期限を超えた `sending`、`unknown`、試行上限に達した `failed` は管理画面で確認する。
- 外部で投稿が見つかった場合はIDとURLを記録する。検索結果に見つからないだけでは再送しない。管理者が媒体側で未投稿と確認したときだけ、手動解決から再試行へ進める。
- 予約時刻直後の配信精度は利用プランと運用スケジュールに依存する。現行の1日1回設定では、実行時刻を過ぎた予約や再試行は次の実行で処理される。

## 停止と復旧

- 後続Cron送信を止めるには、クラウドでCronを停止し、`CRON_PUBLISH_ENABLED` を無効にする。手動実行も止める場合は本番投稿モードを解除する。設定反映を確認する。
- 送信開始後のリクエストは取り消せない場合がある。既に作られた投稿を媒体で確認し、必要に応じて個別の削除承認を取る。
- DB障害時は投稿ID、確保状態、実行時刻を先に記録する。通信断の直後にマイグレーションや投稿を再実行しない。004の復旧は対象DBの依存を確認し、承認済みのロールバック手順を使う。
- ソースの復旧には最新チェックポイント、SHA-256一覧、最新版ソースZIPを使用する。既存の未コミット変更に上書きする前に、差分を手元に退避する。
